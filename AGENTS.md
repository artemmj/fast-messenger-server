# Карта проекта и результаты анализа

## Назначение и архитектура

Проект — асинхронный backend мессенджера на FastAPI, SQLAlchemy и PostgreSQL.
Redis используется в сервисе аутентификации для сохранения access-токенов.
Alembic-миграции находятся в `src/database/migrations/versions`.

Основные потоки:

- `src/routers/auth.py`, `src/routers/user.py` и `src/services/auth.py` /
  `src/services/user.py` реализуют вход, регистрацию и пользовательские API.
- `src/routers/chat.py` и `src/services/chat.py` реализуют личные/групповые
  чаты и членство.
- `src/routers/chat_message.py` и `src/services/chat_message.py` реализуют
  отправку сообщений через REST и постраничную историю.
- `src/routers/websocket.py` принимает подключение и сообщения. Проверка
  членства и запись выполняются сервисом сообщений; затем endpoint получает
  участников через `ChatMembershipDAO` и вызывает `ConnectionManager`.
- `src/services/websocket.py` держит сокеты в локальном словаре
  `user_id -> WebSocket[]`; это не Redis Pub/Sub и не общий брокер событий.
- Модели и схема БД определены в `src/models`; DAО используют `DBDependency`
  из `src/dependencies/db.py`.

### WebSocket-протокол в текущей реализации

Подключение: `GET /ws/chats?token=<JWT>`. После подключения ожидается JSON
объект с `chat_id` и `text`. Успешная отправка создаёт запись и рассылает
участникам:

- `new_message`: `chat_id` и сериализованная запись сообщения;
- `chat_signal`: короткий текст последнего сообщения, время и `sender_id`.

Валидация членства перед отправкой есть в `ChatMessagesService.send_message`.
Отдельных событий подписки/отписки на конкретный чат нет: сокет пользователя
получает сообщения всех чатов, в которых он состоит. История загружается REST
эндпоинтом `/chats/{chat_id}/get_messages`.

## Проблемы по приоритету

Приоритеты отражают влияние на безопасность, корректность и надёжность по
текущему коду. Это результаты статического анализа; в репозитории не обнаружена
папка с тестами, поэтому поведение не подтверждено интеграционными тестами.

### P0 — критично

1. **Публичное изменение привилегий пользователя.** `PATCH /users/{id}` в
   `src/routers/user.py` не использует `get_current_user`, а
   `UserUpdateRequest` в `src/schemas/user.py` допускает `is_superuser`,
   `is_active`, `is_banned` и `is_verified`. Неаутентифицированный клиент может
   менять эти поля у любого пользователя, включая назначение суперпользователя.
   Ограничить маршрут авторизацией и разрешить изменение привилегированных
   полей только доверенной роли/администратору.

### P1 — высокий

1. **Проверка WebSocket-аутентификации слабее REST-проверки.**
   `get_ws_current_user` в `src/dependencies/auth.py` проверяет JWT и извлекает
   `sub`, но не проверяет токен по Redis, наличие пользователя, его активность
   или блокировку. `get_current_user` для REST эти проверки выполняет.
   Следствие: отозванная сессия и токен заблокированного/деактивированного
   аккаунта могут открывать WebSocket до истечения JWT. Согласовать проверки
   для обоих транспортов; не передавать bearer-токен в query string, поскольку
   URL может попадать в логи инфраструктуры.
2. **Несогласованное поведение токена при регистрации.** `UsersService.create`
   создаёт пользователя, а `register_user` самостоятельно выпускает JWT, не
   сохраняя токен через `AuthService._store_access_token`. В результате этот
   токен не проходит REST-проверку `get_current_user`, но принимается
   WebSocket-проверкой, которая Redis не проверяет.
3. **Нет межпроцессной доставки.** `ConnectionManager` использует память одного
   процесса. Если REST-запрос или WebSocket-соединение обслуживается другим
   worker, он не увидит соединения первого. Запуск нескольких worker нарушает
   realtime-доставку; нужен общий Pub/Sub/брокер либо явное ограничение запуска
   одним worker.
4. **Слишком широкие права на добавление участников.** `ChatService.add_member`
   проверяет, что инициатор уже участник, но не проверяет `is_admin`. Любой
   участник группового чата может добавлять других пользователей. Если это
   действие задумано только для администраторов, проверять роль инициатора.
5. **Нет пределов и строгой схемы для WebSocket-сообщений.** Endpoint читает
   произвольный JSON и строит `ChatMessageCreate(text=text)`, где `text` не
   имеет `min_length`/`max_length`; модель БД ограничивает поле 255 символами.
   Нет ограничения частоты отправки или явной обработки неверного JSON.
   Большой/некорректный ввод может приводить к ошибкам БД и ненужной нагрузке.
   Добавить единую схему с согласованными границами, ограничение размера
   кадра/частоты и предсказуемые ошибки протокола.
6. **Раскрытие внутренних ошибок.** В `src/routers/websocket.py` клиенту
   отправляется `str(e)` в поле `e`; это может раскрыть детали SQL/инфраструктуры.
   Возвращать клиенту стабильный код/сообщение, а детали писать в серверный
   logger с безопасным контекстом.

### P2 — средний

1. **Ненадёжная очистка и последовательная рассылка.**
   `websocket_chat_endpoint` очищает соединение только при
   `WebSocketDisconnect`; другие исключения при чтении/обработке могут обойти
   `disconnect`. `send_personal_message` перехватывает ошибки отправки, но не
   удаляет сокет. Рассылка синхронно ожидает каждый сокет и устройство по
   очереди, поэтому медленный клиент задерживает остальных. Нужен `finally`
   для очистки, безопасная идемпотентная регистрация/удаление и изолированная
   отправка с таймаутом.
2. **Дубли членства и личных чатов.** В миграциях нет уникальных ограничений
   `(user_id, chat_id)` для `chatmembership` и на пару участников личного чата.
   Проверка существования личного чата предшествует отдельной транзакции
   создания (`ChatDAO`), поэтому параллельные запросы могут создать несколько
   чатов. Добавить ограничения/идемпотентность и обработку конфликтов.
3. **Различающиеся ошибки отправки через REST и WebSocket.** Сообщение сначала
   фиксируется в БД, затем REST endpoint выполняет realtime-рассылку. Ошибка
   рассылки может вернуть клиенту ошибку запроса, хотя сообщение уже сохранено,
   провоцируя повторную отправку. Разделить результат сохранения и доставки;
   рассмотреть outbox при требованиях надёжной доставки.
4. **Групповой чат может остаться без администратора.** Создатель — единственный
   наделённый `is_admin`, но может выйти через `leave_chat`. Проверки прав
   администратора для управления группой сейчас нет.
5. **Различие ограничений и поведения сообщения.** Пустой текст отбрасывается
   WebSocket-циклом, но REST допускает его; строки длиннее 255 символов не
   запрещены API-схемой и могут завершиться ошибкой БД. Согласовать валидацию
   обоих транспортов.
6. **Нет реализованной обработки прочтения.** У `ChatMessage` есть `is_read`,
   но нет API/событий изменения статуса прочтения.

### P3 — низкий / эксплуатационный

1. В `src/settings.py` безопасные для production значения не обеспечены:
   `DEBUG` по умолчанию включён, `SECRET_KEY` может быть пустым; `.env.example`
   содержит демонстрационные пароли и короткий ключ. Развёртывание должно
   требовать явных секретов и отключённого debug-режима.
2. Список пользователей и получение пользователя по ID в `src/routers/user.py`
   не требуют входа и возвращают контактные поля (телефон/email). Владелец
   аккаунта может обновлять или удалять пользователя без проверки текущего
   пользователя; кроме P0 изменения привилегий, это также раскрытие данных и
   проблема контроля доступа.
3. Проверка лимита групп и проверка существования личного чата выполняются
   отдельно от создания, поэтому лимит группы также обходится параллельными
   запросами. Лимит считает текущие членства с `is_admin`, а не независимую
   запись о создателе.
4. В `src/services/chat_message.py` и других service/DAO встречаются
   несовпадающие аннотации ID (`UUID` против `int`/`str`), а `create_personal_chat`
   DAO может вернуть словарь в ветке существующего чата вместо `Chat`. Привести
   типы и контракт возврата к одному виду.
5. Нет автоматизированных тестов в репозитории. В первую очередь покрыть
   одинаковую авторизацию REST/WebSocket, членство и права, передачу события,
   отключение сокета, границы сообщения и повторные/конкурентные операции.

## Рекомендуемый порядок исправлений

1. Закрыть неавторизованный `PATCH /users/{id}` и ограничить изменение ролей.
2. Унифицировать JWT/сессионную проверку и поведение регистрации для REST и WS.
3. Ввести серверную схему WebSocket-входа, ограничения размера/частоты и
   безопасные ответы ошибок.
4. Определить ожидаемую модель прав группы и применить проверку администратора.
5. Выбрать модель масштабирования WebSocket, затем исправить lifecycle и
   обработку медленных/отвалившихся соединений.
6. Добавить ограничения целостности БД и тесты конкуренции/повторов.
