# Fast Messenger Server

Backend мессенджера на FastAPI: пользователи и JWT-аутентификация, личные и
групповые чаты, история сообщений в PostgreSQL и доставка событий по WebSocket.
Redis хранит выданные при входе токены; миграции схемы управляются Alembic.

## Чаты и WebSocket

`/ws/chats?token=<access_token>` принимает JSON с `chat_id` и `text`. Сообщение
сохраняется в БД, затем участникам чата отправляются события `new_message` и
`chat_signal`. REST API чатов и сообщений находится в `src/routers/chat.py` и
`src/routers/chat_message.py`.

## Известные проблемы по приоритету

- **Критично:** `PATCH /users/{id}` не требует аутентификации и позволяет менять
  `is_superuser`, `is_active` и другие привилегированные поля.
- **Высокий приоритет:** WebSocket проверяет подпись и срок JWT, но не проверяет
  токен/сессию в Redis и статус пользователя. Это отличается от REST-проверки;
  токен передаётся в URL.
- **Высокий приоритет:** WebSocket-рассылка хранится только в памяти процесса.
  При нескольких worker-процессах сообщения не доходят до подключений на других
  процессах.
- **Высокий приоритет:** добавлять участников может любой участник группы,
  проверка администратора отсутствует.
- **Средний приоритет:** WebSocket-входные данные не имеют явных ограничений
  размера/скорости, а ошибки обработки возвращают клиенту текст исключения.
  Ошибки отправки не удаляют отвалившиеся соединения; рассылка выполняется
  последовательно.
- **Средний приоритет:** ограничения уникальности членства и личного чата не
  закреплены в БД, поэтому повторы и параллельные запросы могут создать дубли.
  Сообщения ограничены `VARCHAR(255)` в БД, но схема API это ограничение не
  задаёт.
